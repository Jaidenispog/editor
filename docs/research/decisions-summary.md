## TikTok Content Posting API for a private, single-business app (Studio Assistant, Ivanhoe VIC): Login Kit + Content Posting API requirements, Direct Post vs Upload-to-inbox, audit gate and unaudited limits, media transfer rules, sandbox, developer-account eligibility, music rules, 9:16 specs, and third-party provider routes (Ayrshare, Late/Zernio, Buffer, Zapier).

_Confidence: medium_

Decision: ship the draft/export fallback as the only TikTok path in Stage A/B, and do NOT build a direct Content Posting API integration for Studio Assistant. Reasoning: (1) TikTok's Content Sharing Guidelines explicitly list "a utility tool to help upload contents to the account(s) you or your team manages" as an unacceptable use case and require apps intended for a wide audience, so a private single-barber app is very unlikely to pass the audit; (2) without the audit every API post (Direct Post, and per the guidelines also any unaudited client posting) is forced to SELF_ONLY and requires the TikTok account to be set private at posting time, which is useless for a public business profile; (3) app review itself needs a public, fully developed website with visible Privacy Policy/ToS, verified URL properties, demo videos and a sandbox demonstration, with no approval guarantee; (4) even an audited integration cannot attach TikTok Commercial Sounds to videos, which a Business Account can only add inside the TikTok app. Concretely, Studio Assistant will: render a TikTok-ready export (1080x1920 9:16 MP4, H.264 High profile, AAC 48 kHz, 30 fps, target 8-12 Mbps, under 10 min and well under 4 GB, with caption safe margins), generate a caption up to 2200 characters including hashtags/@mentions, store the caption + export in a "Ready to post" queue with an honest status ("Post in the TikTok app; add a Commercial Sound there"), expose a one-tap download/share and copy-caption flow on the owner's phone, and record "Posted" manually. Music handling: never mix third-party commercial tracks into the TikTok export unless the licence explicitly covers TikTok commercial use (and surface the Music Usage Confirmation wording); default exports to voice/original or licensed library audio, and instruct the owner to pick from Commercial Sounds in-app. Optional Stage C upgrade if the owner wants true auto-publishing: integrate a pre-audited provider behind a feature flag rather than TikTok directly, preferring Buffer (personal API key on the owner's own Buffer account, TikTok channel, schedulingType automatic; low cost) or Zernio (first two connected accounts free, requires content_preview_confirmed and express_consent_given flags, privacy must be from creator's allowed list), with Ayrshare rejected on cost (~US$149/month for one profile) and Zapier rejected because it has no native TikTok publish action. The TikTok for Business "publish a public video post to an owned account" API is the only official self-serve public-posting route for a business, but it requires a company-domain email, a public company website, a Business developer app and (since 20 Mar 2026) an Accounts API access application; park it as a future option only if the owner registers the business as a TikTok for Business developer. Status model for the publishing module must therefore have states: exported, handed-off-to-TikTok-app, posted (manual confirm), and, if the provider flag is on, queued/processing/published/failed with the provider's post id.

Owner must provide or set up:
- Owner must have a TikTok account for the shop; a TikTok Business Account restricts in-app sounds to Commercial Sounds (Commercial Music Library) and TikTok says General Music Library tracks are not cleared for any brand/business content; original/voice audio or externally licensed music requires agreeing to the Music Usage Confirmation.
- Fallback path (chosen): no developer account, app review or audit needed; owner posts the exported MP4 from the TikTok app/TikTok Studio and adds Commercial Sounds there.
- If direct integration is ever attempted: register at developers.tiktok.com (individual accounts allowed but 'not recommended for real app integrations'; create/join an organization for the business, verification needs business certificate + photo ID + proof of representation); create an app with Login Kit + Content Posting API (Direct Post and/or Upload), verified Terms of Service URL, Privacy Policy URL and Web URL (required for apps created after 9 Sep 2024); a public, fully developed website with visible Privacy Policy and ToS links (not a login page); 1-5 demo videos (<=50 MB each) whose domain matches the website URL; sandbox demonstration for a first-time app; then a separate Content Posting API (Direct Post) audit proving UX compliance with the Content Sharing Guidelines - and TikTok lists single-team upload utilities as not acceptable, so expect rejection.
- Until audited (if integrating): only 5 users per 24 h, all posts forced SELF_ONLY, the TikTok account must be set private at posting time; Direct Post ~15 posts/day/creator; Upload mode max 5 pending inbox drafts per 24 h; 6 init requests/min per user token.
- PULL_FROM_URL (if used) requires verifying the hosting domain (DNS signature) or exact https URL prefix (signature file) in the app's URL properties; FILE_UPLOAD avoids this but must follow 5-64 MB chunk rules.
- Provider option (Stage C, optional): Buffer account owned by the business (organization owner creates the personal API key; Free plan has one key, TikTok channel connected via Buffer's own audited app; no TikTok music library/polls; 25 posts/24 h) or Zernio account (first two connected accounts free per Sept 2026 pricing; TikTok connection via Zernio's audited app; consent flags required). Ayrshare starts ~US$149/month for one profile. Zapier cannot publish to TikTok natively.
- TikTok for Business API alternative (future only): TikTok for Business developer registration with a company-domain email and publicly accessible company website matching that domain (individuals not onboarded), a Business developer app, and from 20 Mar 2026 the Accounts API Access Application Form for the 'TikTok Accounts' scope; video URL domain must be verified; 1 GB / 3-600 s / 6 per min / 15 per day.

## Spotify integration feasibility for Studio Assistant (private single-barber-business web app, Ivanhoe VIC, Australia) — Developer Policy/Terms restrictions (AI/ML, previews, third-party transfer, video/sync), Web API changes Nov 2024–Nov 2026 (deprecations, Development Mode, Extended Quota), and whether any permitted private use exists.

_Confidence: medium_

Decision: Studio Assistant CAN offer Spotify only as an optional, narrowly-scoped "mood/genre reference" feature — never as a music source, never as an input to AI, and never in rendered video. Implement it in two tiers and make the limits explicit in the UI.

Tier 0 (default, ship first; no Spotify developer account, no Premium): the owner pastes a Spotify track/album/playlist link. Studio Assistant stores only the Spotify URL/URI plus the owner's own typed labels (e.g., "upbeat afrobeats for Saturday reels"). On display it renders the official Spotify Embed (iframe built from the link, or oEmbed for title/thumbnail fetched at view time, not persisted) with Spotify attribution and the link back to open.spotify.com. The embed plays Spotify's own ~30s preview or the full track for a logged-in Premium viewer — Studio Assistant never touches audio. Nothing from the embed/oEmbed (title, thumbnail, artist) is stored long-term, fed to the planner/LLM, exported, or sent to any third-party service (TikTok/Instagram/Square/email modules must be firewalled from Spotify data; hosting provider only).

Tier 1 (optional, behind a settings toggle with an acknowledgement screen): in-app track search via the Web API in Development Mode, Authorization Code with PKCE (no Implicit Grant, no Client Credentials), GET /search (limit ≤10, paginate with offset) and GET /tracks/{id}. Save only the Spotify URI + owner notes; show name/artist/cover art by re-fetching at view time (temporary cache only), with Spotify logo/icon ≥70px/21px and link-back on every displayed item. Handle 401/invalid_grant (6-month refresh-token expiry → re-sign-in), 403 (owner's Premium lapsed or user not allowlisted → show plain explanation), 429 (rate limit vs reason=QUOTA_EXCEEDED → back off). Provide a Disconnect button that deletes all Spotify-derived data for that user; publish a privacy policy page and show it before the Spotify sign-in. Treat this tier as revocable: the UI must say Spotify describes Development Mode as for learning and non-commercial personal projects and may withdraw access.

Explicitly NOT supported (show as disabled states with honest copy): in-app 30-second previews via the API (preview_url is null/deprecated for new apps), Audio Features/Analysis, Recommendations, Related Artists, editorial/algorithmic playlists; any AI/LLM analysis, mood classification, or planning that ingests Spotify metadata (Policy/Terms "ingest into a machine learning or AI model" ban); any use of Spotify audio in previews, renders or exports (sync and mixing bans); transferring Spotify data to publishing/analytics/third parties; Extended Quota Mode (organizations with ≥250k MAU only — do not plan for it); and in-shop playback (Spotify consumer licence is personal, non-commercial; a commercial background-music service is needed). Music for the videos themselves must come from Studio Assistant's separate licensed-music model, not Spotify.

If the owner declines the Premium/Dev-Mode requirements, Tier 0 still works; if Spotify later tightens embeds or Dev Mode, degrade to link-only (URL + owner notes) rather than breaking.

Owner must provide or set up:
- Tier 0 (embed/link-only): no Spotify developer account, Client ID or Premium needed; comply with the Widget Terms of Use (no local caching of Spotify Content, no game/trivia use, Play Button not for commercial purposes, no circumventing privacy features) and show Spotify attribution/link-back.
- Tier 1 (Web API, Development Mode): a Spotify account for the owner with an ACTIVE Spotify Premium subscription — the app stops working (403) if Premium lapses.
- Tier 1: a Spotify for Developers account linked to that Spotify account, accepting the Developer Terms (v10, eff. 15 May 2025) and Developer Policy (eff. 15 May 2025); create a Development Mode app (Client ID) in the Dashboard — up to 25 Client IDs per account since July 2026, quota pooled across them.
- Tier 1: register the app's HTTPS redirect URI(s) and use Authorization Code with PKCE (Implicit Grant is deprecated); plan for refresh tokens expiring 6 months after each user's original authorization (re-sign-in flow).
- Tier 1: add every user (owner + staff) by name and Spotify email in the app's Users Management tab; hard cap of 5 authorized users per Client ID (unverified whether the owner counts toward the five) — staff without allowlisting get 403.
- Tier 1: publish an end-user privacy policy and display it before Spotify sign-in; provide an in-app Disconnect that deletes Spotify Personal Data; delete all Spotify Content on termination.
- Tier 1: display Spotify Marks for any Spotify content (logo ≥70px or icon ≥21px, link back to the item on Spotify); do not use 'Spotify' or its marks in the product name; do not modify/crop cover art.
- Tier 1: store only Spotify URIs/links plus owner-authored notes; cache metadata/cover art only temporarily; never feed Spotify data to AI/LLM features; never sync/mix Spotify audio with video or other audio; never transfer Spotify data to third parties other than the hosting provider.
- No app review exists or is needed for Development Mode; Extended Quota Mode is NOT attainable (organizations only, company email, legally registered business, launched service, ≥250k MAU, key markets, commercial viability) and should not be planned for.
- Operational: expect Dev Mode quota/rate limits (429 with reason=QUOTA_EXCEEDED vs ordinary rate limiting); Spotify states Development Mode is for learning and non-commercial personal projects and 'should not be relied on as a foundation for building or scaling a business' — the owner must accept that Spotify may revoke or narrow access at any time.
- In-shop music: the owner's Spotify consumer account does not licence playback in a salon/shop; a commercial background-music service (Spotify names its partner Soundtrack) is required — out of scope for Studio Assistant but must not be implied as covered.

## Instagram Reels publishing via the Instagram Platform API (Meta): login variants (Instagram Login vs Facebook Login for Business vs the new Unified Login), permissions and App Review / Development-mode scope, Reels container flow, publishing limits, video specs, error behaviour, and music/audio rules for business accounts

_Confidence: medium_

Build Studio Assistant's Instagram module as a thin adapter over Meta's official container flow, and target the 2026 "API setup with Unified login" for the owner's brand-new Meta app while keeping a legacy "Instagram Login" switch:

1. Auth adapter with two modes behind one interface (`InstagramAuthProvider`):
   - PRIMARY (new apps, Nov 2026): Unified Login = Facebook Login for Business configuration. Login URL https://www.facebook.com/{vNN}/dialog/oauth?client_id=META_APP_ID&config_id=CONFIG_ID&redirect_uri=...&response_type=code&override_default_response_type=true&state=... (no `scope` param). Exchange the code server-side at https://graph.facebook.com/{vNN}/oauth/access_token (client_id, client_secret, redirect_uri, code). Expect a Business Integration System User token; verify with /debug_token (type SYSTEM_USER, expires_at 0 if the configuration is set to "Never"; if 60-day, schedule refresh). Discover the account via GET /me/assigned_instagram_accounts?fields=id,username (fallback GET /me/accounts?fields=instagram_business_account{id,username}); if the list is empty, show the owner the "add business_management to the configuration under Facebook Login for Business > Configurations and reconnect" remediation. All API calls on graph.facebook.com (never graph.instagram.com with this token). Pin one Graph version (v26.0 today) in config.
   - FALLBACK (if the owner's app still has "API setup with Instagram login"): https://www.instagram.com/oauth/authorize with scope=instagram_business_basic,instagram_business_content_publish; exchange at api.instagram.com/oauth/access_token; upgrade with graph.instagram.com/access_token?grant_type=ig_exchange_token; refresh weekly via refresh_access_token?grant_type=ig_refresh_token (token must be >24 h old); alert the owner 7 days before expiry; all calls on graph.instagram.com.
   - Keep the Meta app in Development mode with Standard Access: only the owner (app admin / Instagram Tester, business-portfolio admin) connects, so no App Review and no Business Verification. Do not build a public connect flow.

2. Publishing pipeline (idempotent job per reel, states: rendered -> uploaded -> container_created -> processing -> ready -> publishing -> published | failed | expired):
   - Pre-flight: GET /{ig-id}/content_publishing_limit?fields=quota_usage,config and block when quota_usage >= config.quota_total (plan around 50 even though the guide says 100; show remaining quota in the UI).
   - Host the rendered MP4 (and optional JPEG cover) at a publicly reachable HTTPS URL (object storage with a time-limited signed URL valid at least 2 hours; no auth cookies, correct Content-Type, HTTP 200, Range support).
   - POST /{ig-id}/media with media_type=REELS, video_url, caption (<=2,200 chars, <=30 hashtags), share_to_feed=true by default, optional cover_url or thumb_offset (ms), optional audio_name only when the audio is the shop's own original audio; never claim to attach Instagram library music.
   - Poll GET /{container}?fields=status_code,status,copyright_check_status every 60 s for 5 minutes, then back off to every 5 minutes for up to 24 h (container lifetime); treat IN_PROGRESS as waiting; on FINISHED check copyright_check_status.matches_found and warn the owner before publishing; on ERROR map `status` subcode (2207026 unsupported format -> re-encode; 2207003 download timeout -> retry with fresh URL; 2207050/2207051 -> stop and explain) ; on EXPIRED create a new container.
   - POST /{ig-id}/media_publish?creation_id=...; on 9007/2207027 keep polling (do not recreate); on 9/2207042 quota reached -> queue for next window; on code 100 subcode 33 during polling -> retry with backoff. Then GET /{media-id}?fields=id,permalink,media_product_type and store the permalink.
   - Encode with FFmpeg to the official spec before upload: 1080x1920 (9:16), H.264 High profile yuv420p progressive, closed GOP (e.g. -g 60 -keyint_min 60 -sc_threshold 0), 30 fps (23-60 allowed), VBR <= 25 Mbps (target 8-12 Mbps), AAC 48 kHz 128 kbps stereo, MP4 with -movflags +faststart and no edit lists, duration 3 s-15 min (recommend 15-90 s), file <= 300 MB; validate with ffprobe and refuse to upload otherwise.

3. Music policy in the product: only (a) the shop's own/original audio, (b) tracks the owner holds a commercial licence for, or (c) Meta Sound Collection downloads (allowed only for content that stays on Meta products, so do not reuse those renders on TikTok/YouTube) may be mixed into a reel destined for the API. The UI must state plainly that Instagram library/trending audio cannot be added by the API and cannot be added in the Instagram app after publishing (only "Replace audio" if a track gets muted); offer an "Export for manual posting" path (download the MP4 + copy caption) when the owner wants Instagram-library music, since a Business account in Australia may not even see the licensed library.

4. Honest states and observability: surface quota, token health (type/expiry), container status, copyright match warnings, and Meta error codes verbatim (error_user_msg) in the owner's dashboard; log Graph version and request ids; one retry policy for transient errors, none for policy errors.

Owner must provide or set up:
- Instagram professional account for the barber shop (Business or Creator). Business is recommended; Stories publishing via API is Business-only, and the shop's commercial use already disqualifies the personal licensed music library in practice.
- A Meta developer account (Facebook login) and a new Meta app of type Business with the use case 'Manage messaging & content on Instagram'. Expect the dashboard to say 'API setup with Instagram login is not available for newer apps. Your app uses API setup with Unified login instead.'
- A Meta business portfolio (Business Manager / Meta Business Suite) that owns or has claimed the Instagram account; the app must be connected to that portfolio. The owner must be an admin of the portfolio and must log in through it during the Unified Login flow (System-user access token configurations require business-portfolio login). No Business Verification is needed while the app stays at Standard Access for the owner's own account.
- Facebook Login for Business product + one configuration: Login variation General; Access token = System-user access token; Expiration 'Never' (or 60 days with scheduled refresh); Business assets = Instagram account (ad account optional); Permissions at least instagram_basic and instagram_content_publish (add instagram_manage_insights / instagram_manage_comments if those modules are wanted); add business_management via Facebook Login for Business > Configurations if /me/assigned_instagram_accounts returns empty (community-reported gotcha). Record the config_id and a valid HTTPS OAuth redirect URI.
- App settings required before login works: Privacy Policy URL, User Data Deletion callback/URL, App Domains, and (for Instagram-Login-style setups) deauthorize and data-deletion callback URLs; keep the app in Development mode.
- App roles: the owner (and any staff who will connect) must be an Admin/Developer/Tester on the app and, if the dashboard shows the Instagram Testers section, must be added as an Instagram Tester and accept the invite in the Instagram app (Settings > Website permissions / Apps and websites > Tester invites). Standard Access only covers people with a role on the app.
- No Facebook Page is required for Unified Login or Instagram Login. If the Instagram account is already linked to a Facebook Page, the owner must be able to perform admin-equivalent tasks on that Page and must complete Page Publishing Authorization if Meta prompts for it, or publishing is blocked.
- App Review / Advanced Access is NOT required while the app publishes only to Instagram accounts the owner owns/manages and connected via role holders. If Studio Assistant is ever offered to other barbers, Meta requires App Review with screen recordings per permission plus Business Verification, and the app must be Live.
- Publicly reachable HTTPS hosting for rendered videos and cover images (object storage with signed URLs), since the API fetches video_url itself and does not accept file uploads.
- Music: a documented source for every track mixed into API-published reels: the shop's original audio, tracks the owner has a commercial sync licence for, or Meta Sound Collection downloads (Meta-products-only licence). Instagram library/trending audio is unavailable via API and cannot be added after publishing.
- Operational: respect the per-account publishing quota (read content_publishing_limit; 50 vs 100 per rolling 24 h is inconsistent in Meta's docs), keep the Graph API version pinned and reviewed quarterly, and monitor token health (SUAT 'Never' vs 60-day expiry; Instagram Login tokens must be refreshed before 60 days).

## Square Bookings API for an Australian barber using Square Appointments (Studio Assistant, Ivanhoe VIC) — availability, plan gating, OAuth scopes, endpoints, statuses, webhooks + signature verification, sandbox, Node SDK, and how to tell whether an appointment happened/was paid.

_Confidence: medium_

Build the Square module in two capability tiers and gate the second at runtime.

TIER 0 — implement now; works on Square Appointments Free (and any plan):
- Auth: single-seller private app. Store the owner's Square production access token (or OAuth token) server-side; use `square@^46.0.0` (Node >= 18): `new SquareClient({ token, environment: SquareEnvironment.Production | Sandbox })`; leave Square-Version at the SDK default (2026-09-16) and pin only if a response shape changes.
- Reads (scopes APPOINTMENTS_READ + APPOINTMENTS_ALL_READ + APPOINTMENTS_BUSINESS_SETTINGS_READ + CUSTOMERS_READ + ITEMS_READ + MERCHANT_PROFILE_READ + PAYMENTS_READ + ORDERS_READ): `bookings.list` in <=31-day windows with cursor pagination (poll every 5–15 min, plus a nightly reconciliation of the past/next 31 days); `bookings.get`/`bulkRetrieveBookings`; `bookings.searchAvailability` (24h–32-day ranges; use `booking_id` filter for reschedule previews); `bookings.getBusinessProfile` (cache `support_seller_level_writes`, `booking_policy`, cancellation settings); `bookings.teamMemberProfiles.list` (filter `is_bookable`); `bookings.locationProfiles.list` (show `booking_site_url`); Catalog search for `product_type = APPOINTMENTS_SERVICE` with `service_duration`, `available_for_booking`, `team_member_ids`; Customers retrieve/search for names; Payments/Orders list for the attendance heuristic.
- Webhooks: one subscription for booking.created, booking.updated, payment.created, payment.updated, customer.created/updated/deleted. Verify with `await WebhooksHelper.verifySignature({ requestBody: rawBodyString, signatureHeader: req.headers['x-square-hmacsha256-signature'], signatureKey, notificationUrl })` using the raw body (no JSON.parse first) and the exact notification URL configured in the Developer Console (watch trailing slashes); dedupe on `event_id`; treat each event as a trigger to re-fetch the booking (authoritative), never as the sole source of truth (missed booking.created events are reported).
- Status model: mirror Square's six statuses verbatim and derive local views: Upcoming (ACCEPTED, start_at in future), Needs action (PENDING), Cancelled (CANCELLED_BY_CUSTOMER / CANCELLED_BY_SELLER / DECLINED), No-show (NO_SHOW), Past (ACCEPTED with start_at + duration in the past). Never present "completed" as a Square fact.
- "Did it happen / was it paid?" heuristic (clearly labelled as inferred): for a Past booking, look for a COMPLETED Payment at the same location within [start_at − 30 min, start_at + duration + ~3 h] whose `customer_id` matches, preferring payments whose `application_details.square_product == 'APPOINTMENTS'` and whose Order line items include `catalog_object_id == appointment_segments[].service_variation_id`; score by matches (customer, service, team_member_id, time). Expose states: Attended & paid (match found), Attended – no payment matched, No-show (NO_SHOW), Cancelled. Let the owner confirm/override locally and persist the owner's override.

TIER 1 — implement behind a runtime gate (requires Appointments Plus or Premium; scopes APPOINTMENTS_WRITE + APPOINTMENTS_ALL_WRITE, plus CUSTOMERS_WRITE if the app creates customers):
- Enable Create/Reschedule/Cancel UI only when `getBusinessProfile().support_seller_level_writes === true`; on a 403 from a write, flip the module to read-only and explain that a paid Appointments plan is required.
- `bookings.create` (seller-level → booking is ACCEPTED immediately; supply idempotency_key, location_id, start_at, customer_id, appointment_segments[{ team_member_id, service_variation_id, service_variation_version, duration_minutes }]); `bookings.update` for reschedule (send `version`; use searchAvailability with `booking_id` first); `bookings.cancel` with `booking_version`.
- Known hard limits to surface in UI: (a) the API cannot mark NO_SHOW or otherwise change `status` — the owner must do that in Square Appointments; (b) services carrying a non-zero no-show fee cannot be booked through the API — if the owner uses Plus no-show protection on a service, API booking for that service will fail, so either keep those bookings in Square's own channels or keep fee-free variations for staff-made bookings; (c) deposits/payments cannot be attached to a booking via API.

DO NOT build buyer-level writes (APPOINTMENTS_WRITE alone) for the staff tool: they create PENDING "customer" bookings and the app only sees its own bookings. (This is the only Free-plan write path and could later back a customer-facing widget.)

Testing: use the sandbox (connect.squareupsandbox.com); onboard the default sandbox test account to Appointments in the Sandbox Dashboard, seed APPOINTMENTS_SERVICE items and bookable team members, optionally subscribe the sandbox account to Appointments Plus with a test card (never charged) to exercise Tier 1, and use Developer Console test events plus real sandbox booking changes for webhooks.

Owner must provide or set up:
- Square seller account in Australia with Square Appointments activated (one-time in Square Dashboard). The Free plan (A$0, unlimited staff per AU pricing page) is enough for Tier 0 reads + webhooks.
- For Tier 1 seller-level create/update/cancel via API: an active or trial Square Appointments Plus (A$40/mo per location, AU) or Premium (A$90/mo per location, AU) subscription; confirm with RetrieveBusinessBookingProfile.support_seller_level_writes === true. Without it, seller-level writes return 403.
- Square Developer account and an application in the Developer Console; for the owner's own account use the app's production access token (or complete OAuth with scopes: APPOINTMENTS_READ, APPOINTMENTS_ALL_READ, APPOINTMENTS_BUSINESS_SETTINGS_READ, CUSTOMERS_READ, ITEMS_READ, MERCHANT_PROFILE_READ, PAYMENTS_READ, ORDERS_READ; add APPOINTMENTS_WRITE + APPOINTMENTS_ALL_WRITE for Tier 1 and CUSTOMERS_WRITE if creating customers). APPOINTMENTS_ALL_* must be accompanied by APPOINTMENTS_READ/WRITE respectively.
- Webhook subscription in the Developer Console pointing to a public HTTPS notification URL of Studio Assistant, subscribed to booking.created, booking.updated, payment.created, payment.updated, customer.created/updated/deleted; store the subscription's signature key as a secret; the notification URL string used for verification must exactly match the one configured.
- No Square App Marketplace listing or app review is needed for a private, single-seller integration used only by the owner's own account (standard Square practice; not re-verified this session because the docs host was blocked).
- Catalog hygiene in Square: services must be APPOINTMENTS_SERVICE items with variations having service_duration, available_for_booking = true and team_member_ids; team members must exist in Square Team and be bookable (TeamMemberBookingProfile.is_bookable). Services with a non-zero no-show fee cannot be booked via the API.
- Sandbox for development: default sandbox test account onboarded to Square Appointments via the Sandbox Dashboard; optional sandbox Appointments Plus/Premium subscription with a test card (sandbox is free of charge).
- Runtime: Node.js >= 18 and the `square` npm package v46.x (API version 2026-09-16); raw-body capture on the webhook route for signature verification.

## Google Business Profile (reviews, review link, solicitation policy, Performance API) and Google Search Console API for Studio Assistant (single barber business, Ivanhoe VIC)

_Confidence: medium_

Build the Google integration in three independent tiers so the app is useful with zero Google approvals and only lights up extra metrics when an authorised integration exists.

Tier 0 (ships now, no Google API, no approval): link-based review requests. Settings screen asks the owner to paste the review link copied from the Business Profile dashboard (Read Reviews > Get more reviews > share icon, desktop only) and optionally the Place ID. Store the pasted link verbatim; never synthesise g.page/r/... or search.google.com/local/writereview?placeid=... URLs (both undocumented). Requests go out through Studio Assistant's own SMS/email channel after an appointment, to every opted-in client uniformly (no filtering by satisfaction, no pre-screen 'how was it?' question, no incentive copy, no per-staff targets). Wording is neutral: ask for an honest review of their experience. Tracking is first-party only: requests sent, delivered, link clicks via an app-owned redirect (/r/<token> -> 302 to the stored official link; the redirect must not gate or branch on anything), and an optional manual 'review received' tick by the owner. UI guardrails: a short policy notice on the compose screen, no 'send only to happy clients' control, and copy templates that avoid any reward language (Google policy + ACCC).

Tier 1 (optional, Maps Platform key only, no GBP approval): if the owner adds a restricted Google Maps Platform API key and Place ID, call Places API (New) Place Details with field mask googleMapsLinks,rating,userRatingCount once a day (far below the 5,000/month Pro free cap). Use googleMapsLinks.writeAReviewUri as the canonical review link (fall back to the pasted link), show current star rating and review count on the dashboard, cache only the Place ID indefinitely and keep the latest rating/count snapshot with its fetch time (treat as a display cache, not a historical series, until the caching terms are checked). Do not request the reviews field (Enterprise + Atmosphere SKU, 1,000/month cap, caching restrictions) in this tier.

- Resend fallback account (only if Postmark approval is refused): verify the domain in Resend (Free: 3,000 emails/month, 100/day, 3 domains, 1 webhook endpoint, 30-day retention); Pro at USD $20/month removes the daily cap; on Resend the app must add List-Unsubscribe and List-Unsubscribe-Post headers itself and host the RFC 8058 POST endpoint, or use Resend Broadcasts/Segments.

## Vertical video safe zones and export specs for TikTok and Instagram Reels (1080x1920) for Studio Assistant

_Confidence: medium_

Studio Assistant renders at exactly 1080x1920 (9:16, square pixels) and uses ONE layout model that is the conservative union of Meta's official percentages (14% top / 35% bottom / 6% sides) and the most conservative widely-cited reading of TikTok's official in-feed template (240 top / 660 bottom / 120 sides / 300 px right in the lower frame). Pixel decisions (origin top-left):

UI EXCLUSION BANDS (never place text, logos, CTAs, subtitles here):
- Top band: y < 270 (IG 14% = 269; TikTok 240).
- Bottom band: y >= 1248 (IG 35% = 672 px from bottom; TikTok 660).
- Side bleed: x < 120 and x > 960 everywhere (TikTok 120; IG 65).
- Right action-button column: x > 780 for y >= 840 (TikTok 180-px icon column inside the 120-px margin from y~840; IG lower-right block ~21%/227 px wide in the bottom 40%).

TEXT-SAFE RECTANGLES exposed to the planner/renderer:
- R_strict (default for everything): x 120-780, y 270-1248 (660 x 978). Any text box the renderer emits must be fully inside R_strict unless it qualifies for R_head.
- R_head (titles/hooks/logos whose box bottom <= 840): x 120-960, y 270-840 (840 x 570). This is clear of both platforms' button columns.
- Subtitles/captions: centred at x = 540, max width 480 (x 300-780), bottom-anchored with box bottom <= 1248 (default baseline band y 1100-1248), minimum font size 56 px, 2-3 words per line, drop-shadow or pill background for legibility. Centring at 540 with 480 width keeps them centred on screen while still inside R_strict.
- Logo/watermark: top-right of R_head, right edge at x 960, top at y 270 (clear of both top bars and the right-hand icons). Never a third-party-style watermark (hurts IG recommendations).
- Subject framing (soft, not enforced): keep faces/the haircut within y 270-1440 and x 0-940; the UI overlays are translucent so partial overlap of the subject is tolerable, text is not.
- Previews: overlay a dimmed-band PNG of the exclusion bands (two toggles: 'TikTok' and 'Reels') on the five preview renders so the owner can see what the apps cover; the exported file never contains the overlay.

EXPORT PRESET (single universal file for both platforms; FFmpeg):
- Scale/crop every source to 1080x1920 (crop, never letterbox; setsar=1). Do not export 4K (IG max width 1920 would reject a 2160-wide file).
- Video: libx264, -profile:v high, -level 4.1 at <=30 fps or 4.2 at 60 fps, -pix_fmt yuv420p, progressive, constant frame rate (-fps_mode cfr). Default 30 fps (satisfies IG Help 'minimum 30 FPS', IG API 23-60, FB Reels 24-60, TikTok API 23-60); offer 60 fps only when every source clip is >=50 fps; 24/25/50 fps sources are conformed to 30 (or 60). Closed GOP of 2 s (-g 60/-keyint_min 60 at 30 fps, -g 120 at 60 fps, -sc_threshold 0, open_gop=0), -preset slow, -crf 18 with VBV cap -maxrate 20M -bufsize 40M (30 fps) or -maxrate 24M -bufsize 48M (60 fps); peak stays under IG's 25 Mbps max and far above TikTok's 516/2,500 kbps minimums. Colour: SDR only, tag -color_primaries bt709 -color_trc bt709 -colorspace bt709 -color_range tv; tone-map HDR sources (iPhone HLG/Dolby Vision 8.4, PQ) to BT.709 at ingest (zscale/tonemap or libplacebo). No HDR export because TikTok's HDR handling is undocumented.
- Audio: AAC-LC, 48 kHz, 2 channels, 128 kbps (the literal IG value and FB '128kbps+'), loudness-normalised (-14 LUFS integrated target), single audio track.
- Container: MP4, -movflags +faststart+negative_cts_offsets -use_editlist 0 (moov atom at the front, no edit lists, per IG spec), one video + one audio track, .mp4 extension (TikTok web upload does not list MOV).
- Duration: min 5 s; templates target 15-60 s; hard cap 180 s (3 min) so the file is eligible for IG recommendation to new audiences and fits every TikTok creator tier (3-minute floor, max_video_post_duration_sec); warn when > 90 s (IG boost limit). For 90-180 s exports lower -maxrate to 12M so the file stays under 300 MB.
- File size guard: reject/re-encode if > 300 MB (IG API max); this automatically satisfies TikTok ads (500 MB), TikTok API (4 GB) and TikTok Studio (10 GB).
- Post-export validation (ffprobe): 1080x1920, yuv420p, h264 High@4.1/4.2, CFR 30 or 60, GOP <= 2 s closed, AAC 48 kHz stereo, bt709 tags, moov before mdat, no elst, duration 5-180 s, size <= 300 MB. Fail the job with a plain-language message if any check fails.
- Store the safe-zone constants in one shared module (packages/video/safe-zones) with the source citations as comments and a 'reviewed on' date, since both platforms change UI without notice; recheck roughly every 6 months by downloading TikTok's in-feed safe-zone ZIP and Meta's Reels safe-zone checker and re-measuring.

Owner must provide or set up:
- Stage A (manual posting, the owner uploads the exported MP4 from their phone or TikTok Studio): no developer or ad accounts needed. TikTok Studio web upload accepts MP4/WebM, >=720x1280, <=30 min, <10 GB; the owner should turn on 'Upload HD' (1080p, select countries). Instagram app upload: 9:16, >=720 px, >=30 fps per Help Center.
- If Studio Assistant later auto-publishes to TikTok (Content Posting API): a TikTok for Developers app with the Content Posting API product and video.publish (direct post) and/or video.upload scopes, user OAuth per staff account, a query to creator_info before every post to honour max_video_post_duration_sec and the creator's privacy options, chunked upload rules (5-64 MB chunks, <=1000 chunks, <=4 GB), rate limits (6 requests/min per user token, <=5 pending shares per 24 h), and file restrictions (MP4 H.264 recommended, 23-60 fps, 360-4096 px, <=10 min). Known from TikTok's docs but NOT re-verified this session: unaudited apps can only post with private (SELF_ONLY) visibility until the app passes TikTok's audit, so public direct posting requires app review.
- If Studio Assistant later auto-publishes Reels (Instagram Graph API / Instagram API with Instagram Login): the barber's Instagram must be a professional (Business or Creator) account (standard Meta requirement; not re-verified this session), a Meta app with the content-publishing permission (instagram_business_content_publish or instagram_content_publish) which needs Meta App Review/advanced access to publish for accounts outside the app's test roles, a publicly reachable HTTPS video_url (or a resumable upload session) for the REELS container, compliance with the Reel spec (moov atom first, no edit lists, <=25 Mbps, 3 s-15 min, <=300 MB), and the per-account cap of 100 (docs also say 50) API-published posts per 24-hour moving period.

Ad safe zones are stricter than organic and are already covered by R_strict.
- Music: platforms' commercial-music rules are out of scope here, but exported audio must be a single AAC-LC 48 kHz stereo track; keep the licensing model from the other research thread in mind before adding any music bed.
