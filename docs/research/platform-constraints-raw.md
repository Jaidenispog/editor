## TikTok Content Posting API for a private, single-business app (Studio Assistant, Ivanhoe VIC): Login Kit + Content Posting API requirements, Direct Post vs Upload-to-inbox, audit gate and unaudited limits, media transfer rules, sandbox, developer-account eligibility, music rules, 9:16 specs, and third-party provider routes (Ayrshare, Late/Zernio, Buffer, Zapier).
Confidence: **medium**

**Decision:** Decision: ship the draft/export fallback as the only TikTok path in Stage A/B, and do NOT build a direct Content Posting API integration for Studio Assistant. Reasoning: (1) TikTok's Content Sharing Guidelines explicitly list "a utility tool to help upload contents to the account(s) you or your team manages" as an unacceptable use case and require apps intended for a wide audience, so a private single-barber app is very unlikely to pass the audit; (2) without the audit every API post (Direct Post, and per the guidelines also any unaudited client posting) is forced to SELF_ONLY and requires the TikTok account to be set private at posting time, which is useless for a public business profile; (3) app review itself needs a public, fully developed website with visible Privacy Policy/ToS, verified URL properties, demo videos and a sandbox demonstration, with no approval guarantee; (4) even an audited integration cannot attach TikTok Commercial Sounds to videos, which a Business Account can only add inside the TikTok app. Concretely, Studio Assistant will: render a TikTok-ready export (1080x1920 9:16 MP4, H.264 High profile, AAC 48 kHz, 30 fps, target 8-12 Mbps, under 10 min and well under 4 GB, with caption safe margins), generate a caption up to 2200 characters including hashtags/@mentions, store the caption + export in a "Ready to post" queue with an honest status ("Post in the TikTok app; add a Commercial Sound there"), expose a one-tap download/share and copy-caption flow on the owner's phone, and record "Posted" manually. Music handling: never mix third-party commercial tracks into the TikTok export unless the licence explicitly covers TikTok commercial use (and surface the Music Usage Confirmation wording); default exports to voice/original or licensed library audio, and instruct the owner to pick from Commercial Sounds in-app. Optional Stage C upgrade if the owner wants true auto-publishing: integrate a pre-audited provider behind a feature flag rather than TikTok directly, preferring Buffer (personal API key on the owner's own Buffer account, TikTok channel, schedulingType automatic; low cost) or Zernio (first two connected accounts free, requires content_preview_confirmed and express_consent_given flags, privacy must be from creator's allowed list), with Ayrshare rejected on cost (~US$149/month for one profile) and Zapier rejected because it has no native TikTok publish action. The TikTok for Business "publish a public video post to an owned account" API is the only official self-serve public-posting route for a business, but it requires a company-domain email, a public company website, a Business developer app and (since 20 Mar 2026) an Accounts API access application; park it as a future option only if the owner registers the business as a TikTok for Business developer. Status model for the publishing module must therefore have states: exported, handed-off-to-TikTok-app, posted (manual confirm), and, if the provider flag is on, queued/processing/published/failed with the provider's post id.

**Account / plan / review requirements:**
- Owner must have a TikTok account for the shop; a TikTok Business Account restricts in-app sounds to Commercial Sounds (Commercial Music Library) and TikTok says General Music Library tracks are not cleared for any brand/business content; original/voice audio or externally licensed music requires agreeing to the Music Usage Confirmation.

**Uncertainties:**
- Every source was read via web-search summaries, not full pages: developers.tiktok.com, ayrshare.com, getlate.dev, buffer.com and zapier.com all failed DNS resolution in this sandbox (hosts must be allowed in the session's network settings to fetch them directly). Quoted wording is as surfaced by the search tool and should be re-checked on the live pages before implementation.
- Whether the Upload-to-inbox (video.upload) mode is also subject to the unaudited 'account must be private / SELF_ONLY' rule is not fully settled: the Content Sharing Guidelines wording and the unaudited_client_can_only_post_to_private_accounts error are documented on the Direct Post pages; some third-party integrators claim inbox drafts are exempt. Treat Upload mode as audit-gated unless verified in a sandbox.
- Official TikTok pages show no visible 'last updated' dates; the search index copies were ~97 days old. One search summary referred to the docs as 'last updated August 2026' but that could not be confirmed. No 2025-2026 Content Posting API changelog entries were found, so changes may exist that the index missed.
- Audit turnaround (third-party reports: several days to two weeks) and the exact post-audit caps are unofficial; TikTok publishes no timeline and says approval is not guaranteed.
- The exact rendering of the audit application form (Products > Content Posting API > Direct Post > Apply) and whether organization/business verification is mandatory for the audit come from third-party guides, not official docs.
- TikTok's own docs are internally inconsistent on some limits: spam_risk_too_many_posts is listed as HTTP 200 on the creator_info page but 403 on Direct Post; status-fetch rate limit (30/min) and the 15-25 posts/day figures are partly from third parties.
- Claims about automatic muting of non-Commercial-Music-Library audio on Business Accounts since July 25, 2025 come from music-vendor blogs; no official TikTok page confirming the date or mechanism was found.
- Ayrshare, Zernio and Buffer pricing figures are from third-party review/competitor sites (2026 snapshots) and may be outdated; none of these vendors was confirmed as a TikTok Marketing Partner. Buffer's statement that OAuth app clients are available conflicts with a third-party claim that third-party OAuth on the new API is not yet enabled (irrelevant if the owner uses a personal API key).
- Whether Buffer's API createPost (marked experimental) supports TikTok automatic publishing with video media end-to-end was not verified.
- No Australia-specific restrictions on TikTok developer registration were found, but regional availability of the Developer Portal and of the Commercial Music Library catalogue was not explicitly checked.

## Spotify integration feasibility for Studio Assistant (private single-barber-business web app, Ivanhoe VIC, Australia) — Developer Policy/Terms restrictions (AI/ML, previews, third-party transfer, video/sync), Web API changes Nov 2024–Nov 2026 (deprecations, Development Mode, Extended Quota), and whether any permitted private use exists.
Confidence: **medium**

**Decision:** Decision: Studio Assistant CAN offer Spotify only as an optional, narrowly-scoped "mood/genre reference" feature — never as a music source, never as an input to AI, and never in rendered video. Implement it in two tiers and make the limits explicit in the UI.

Tier 0 (default, ship first; no Spotify developer account, no Premium): the owner pastes a Spotify track/album/playlist link. Studio Assistant stores only the Spotify URL/URI plus the owner's own typed labels (e.g., "upbeat afrobeats for Saturday reels"). On display it renders the official Spotify Embed (iframe built from the link, or oEmbed for title/thumbnail fetched at view time, not persisted) with Spotify attribution and the link back to open.spotify.com. The embed plays Spotify's own ~30s preview or the full track for a logged-in Premium viewer — Studio Assistant never touches audio. Nothing from the embed/oEmbed (title, thumbnail, artist) is stored long-term, fed to the planner/LLM, exported, or sent to any third-party service (TikTok/Instagram/Square/email modules must be firewalled from Spotify data; hosting provider only).

Tier 1 (optional, behind a settings toggle with an acknowledgement screen): in-app track search via the Web API in Development Mode, Authorization Code with PKCE (no Implicit Grant, no Client Credentials), GET /search (limit ≤10, paginate with offset) and GET /tracks/{id}. Save only the Spotify URI + owner notes; show name/artist/cover art by re-fetching at view time (temporary cache only), with Spotify logo/icon ≥70px/21px and link-back on every displayed item. Handle 401/invalid_grant (6-month refresh-token expiry → re-sign-in), 403 (owner's Premium lapsed or user not allowlisted → show plain explanation), 429 (rate limit vs reason=QUOTA_EXCEEDED → back off). Provide a Disconnect button that deletes all Spotify-derived data for that user; publish a privacy policy page and show it before the Spotify sign-in. Treat this tier as revocable: the UI must say Spotify describes Development Mode as for learning and non-commercial personal projects and may withdraw access.

Explicitly NOT supported (show as disabled states with honest copy): in-app 30-second previews via the API (preview_url is null/deprecated for new apps), Audio Features/Analysis, Recommendations, Related Artists, editorial/algorithmic playlists; any AI/LLM analysis, mood classification, or planning that ingests Spotify metadata (Policy/Terms "ingest into a machine learning or AI model" ban); any use of Spotify audio in previews, renders or exports (sync and mixing bans); transferring Spotify data to publishing/analytics/third parties; Extended Quota Mode (organizations with ≥250k MAU only — do not plan for it); and in-shop playback (Spotify consumer licence is personal, non-commercial; a commercial background-music service is needed). Music for the videos themselves must come from Studio Assistant's separate licensed-music model, not Spotify.

If the owner declines the Premium/Dev-Mode requirements, Tier 0 still works; if Spotify later tightens embeds or Dev Mode, degrade to link-only (URL + owner notes) rather than breaking.

**Decision:** Build Studio Assistant's Instagram module as a thin adapter over Meta's official container flow, and target the 2026 "API setup with Unified login" for the owner's brand-new Meta app while keeping a legacy "Instagram Login" switch:

1. Auth adapter with two modes behind one interface (`InstagramAuthProvider`):

## Square Bookings API for an Australian barber using Square Appointments (Studio Assistant, Ivanhoe VIC) — availability, plan gating, OAuth scopes, endpoints, statuses, webhooks + signature verification, sandbox, Node SDK, and how to tell whether an appointment happened/was paid.
Confidence: **medium**

**Decision:** Build the Square module in two capability tiers and gate the second at runtime.

TIER 0 — implement now; works on Square Appointments Free (and any plan):
- Auth: single-seller private app. Store the owner's Square production access token (or OAuth token) server-side; use `square@^46.0.0` (Node >= 18): `new SquareClient({ token, environment: SquareEnvironment.Production | Sandbox })`; leave Square-Version at the SDK default (2026-09-16) and pin only if a response shape changes.
- Reads (scopes APPOINTMENTS_READ + APPOINTMENTS_ALL_READ + APPOINTMENTS_BUSINESS_SETTINGS_READ + CUSTOMERS_READ + ITEMS_READ + MERCHANT_PROFILE_READ + PAYMENTS_READ + ORDERS_READ): `bookings.list` in <=31-day windows with cursor pagination (poll every 5–15 min, plus a nightly reconciliation of the past/next 31 days); `bookings.get`/`bulkRetrieveBookings`; `bookings.searchAvailability` (24h–32-day ranges; use `booking_id` filter for reschedule previews); `bookings.getBusinessProfile` (cache `support_seller_level_writes`, `booking_policy`, cancellation settings); `bookings.teamMemberProfiles.list` (filter `is_bookable`); `bookings.locationProfiles.list` (show `booking_site_url`); Catalog search for `product_type = APPOINTMENTS_SERVICE` with `service_duration`, `available_for_booking`, `team_member_ids`; Customers retrieve/search for names; Payments/Orders list for the attendance heuristic.
- Webhooks: one subscription for booking.created, booking.updated, payment.created, payment.updated, customer.created/updated/deleted. Verify with `await WebhooksHelper.verifySignature({ requestBody: rawBodyString, signatureHeader: req.headers['x-square-hmacsha256-signature'], signatureKey, notificationUrl })` using the raw body (no JSON.parse first) and the exact notification URL configured in the Developer Console (watch trailing slashes); dedupe on `event_id`; treat each event as a trigger to re-fetch the booking (authoritative), never as the sole source of truth (missed booking.created events are reported).
- Status model: mirror Square's six statuses verbatim and derive local views: Upcoming (ACCEPTED, start_at in future), Needs action (PENDING), Cancelled (CANCELLED_BY_CUSTOMER / CANCELLED_BY_SELLER / DECLINED), No-show (NO_SHOW), Past (ACCEPTED with start_at + duration in the past). Never present "completed" as a Square fact.
- "Did it happen / was it paid?" heuristic (clearly labelled as inferred): for a Past booking, look for a COMPLETED Payment at the same location within [start_at − 30 min, start_at + duration + ~3 h] whose `customer_id` matches, preferring payments whose `application_details.square_product == 'APPOINTMENTS'` and whose Order line items include `catalog_object_id == appointment_segments[].service_variation_id`; score by matches (customer, service, team_member_id, time). Expose states: Attended & paid (match found), Attended – no payment matched, No-show (NO_SHOW), Cancelled. Let the owner confirm/override locally and persist the owner's override.

TIER 1 — implement behind a runtime gate (requires Appointments Plus or Premium; scopes APPOINTMENTS_WRITE + APPOINTMENTS_ALL_WRITE, plus CUSTOMERS_WRITE if the app creates customers):
- Enable Create/Reschedule/Cancel UI only when `getBusinessProfile().support_seller_level_writes === true`; on a 403 from a write, flip the module to read-only and explain that a paid Appointments plan is required.
- `bookings.create` (seller-level → booking is ACCEPTED immediately; supply idempotency_key, location_id, start_at, customer_id, appointment_segments[{ team_member_id, service_variation_id, service_variation_version, duration_minutes }]); `bookings.update` for reschedule (send `version`; use searchAvailability with `booking_id` first); `bookings.cancel` with `booking_version`.
- Known hard limits to surface in UI: (a) the API cannot mark NO_SHOW or otherwise change `status` — the owner must do that in Square Appointments; (b) services carrying a non-zero no-show fee cannot be booked through the API — if the owner uses Plus no-show protection on a service, API booking for that service will fail, so either keep those bookings in Square's own channels or keep fee-free variations for staff-made bookings; (c) deposits/payments cannot be attached to a booking via API.

DO NOT build buyer-level writes (APPOINTMENTS_WRITE alone) for the staff tool: they create PENDING "customer" bookings and the app only sees its own bookings. (This is the only Free-plan write path and could later back a customer-facing widget.)

Testing: use the sandbox (connect.squareupsandbox.com); onboard the default sandbox test account to Appointments in the Sandbox Dashboard, seed APPOINTMENTS_SERVICE items and bookable team members, optionally subscribe the sandbox account to Appointments Plus with a test card (never charged) to exercise Tier 1, and use Developer Console test events plus real sandbox booking changes for webhooks.

## Google Business Profile (reviews, review link, solicitation policy, Performance API) and Google Search Console API for Studio Assistant (single barber business, Ivanhoe VIC)
Confidence: **medium**

**Decision:** Build the Google integration in three independent tiers so the app is useful with zero Google approvals and only lights up extra metrics when an authorised integration exists.

Tier 0 (ships now, no Google API, no approval): link-based review requests. Settings screen asks the owner to paste the review link copied from the Business Profile dashboard (Read Reviews > Get more reviews > share icon, desktop only) and optionally the Place ID. Store the pasted link verbatim; never synthesise g.page/r/... or search.google.com/local/writereview?placeid=... URLs (both undocumented). Requests go out through Studio Assistant's own SMS/email channel after an appointment, to every opted-in client uniformly (no filtering by satisfaction, no pre-screen 'how was it?' question, no incentive copy, no per-staff targets). Wording is neutral: ask for an honest review of their experience. Tracking is first-party only: requests sent, delivered, link clicks via an app-owned redirect (/r/<token> -> 302 to the stored official link; the redirect must not gate or branch on anything), and an optional manual 'review received' tick by the owner. UI guardrails: a short policy notice on the compose screen, no 'send only to happy clients' control, and copy templates that avoid any reward language (Google policy + ACCC).

Tier 1 (optional, Maps Platform key only, no GBP approval): if the owner adds a restricted Google Maps Platform API key and Place ID, call Places API (New) Place Details with field mask googleMapsLinks,rating,userRatingCount once a day (far below the 5,000/month Pro free cap). Use googleMapsLinks.writeAReviewUri as the canonical review link (fall back to the pasted link), show current star rating and review count on the dashboard, cache only the Place ID indefinitely and keep the latest rating/count snapshot with its fetch time (treat as a display cache, not a historical series, until the caching terms are checked). Do not request the reviews field (Enterprise + Atmosphere SKU, 1,000/month cap, caching restrictions) in this tier.

Tier 2 (only when 'Google Business Profile (API)' is connected): requires an approved Cloud project (quota shows 300 QPM, not 0) and the owner's OAuth grant with scope https://www.googleapis.com/auth/business.manage. Resolve IDs via Account Management accounts.list and Business Information accounts.locations.list (readMask=name,title), then: list reviews with v4 accounts.locations.reviews.list (pageSize 50, order by updateTime desc, tolerate the documented pagination inconsistency by re-syncing on updateTime watermark), reply from the app via updateReply (enforce 4096 bytes, surface reviewReplyState/policyViolation from the list response), and ingest new reviews either by polling or via Notifications API Pub/Sub (NEW_REVIEW, UPDATED_REVIEW). Performance panel via Business Profile Performance API fetchMultiDailyMetricsTimeSeries: search/maps impressions (desktop+mobile), BUSINESS_DIRECTION_REQUESTS, CALL_CLICKS, WEBSITE_CLICKS, BUSINESS_BOOKINGS, MESSAGING_CLICKS (added Oct 2026), plus searchkeywords.impressions.monthly (monthly, up to 5-day lag). Do not reference BUSINESS_CONVERSATIONS (removed 2026-01-31) or the Q&A API (discontinued 2025-11-03). When not connected, show an honest 'Not connected - metrics available only through an approved Business Profile API integration' state with a link to the GBP dashboard; never show placeholder numbers.

Tier 3 (optional, separate): Search Console integration with scope webmasters.readonly after the owner verifies the shop website (prefer a Domain property with DNS TXT). Show clicks, impressions, CTR, average position by query/page/date with a 2-3 day lag note and 16-month history; sites.list first to confirm the property and permission level.

OAuth app setup: one Cloud project, External consent screen published to Production (not left in Testing, which kills refresh tokens after 7 days and would break background sync), owner is the only user so the 100-user cap is irrelevant; if the console flags business.manage as sensitive, either accept the unverified-app warning for the single owner account or complete sensitive-scope verification; use Internal user type instead if the owner has Google Workspace. Store refresh tokens encrypted, detect invalid_grant and prompt reconnect. Feature-flag each tier and record integration status per tier in the DB so dashboards can state exactly which metrics come from which authorised source.

## Supabase as deployment target for Studio Assistant: Postgres (Supavisor/direct connections for a Node pg-boss worker) + private media storage (Supabase Storage S3 protocol vs Cloudflare R2)
Confidence: **high**

**Decision:** Recommended Studio Assistant configuration (decision):

1. Supabase Pro project in Sydney (ap-southeast-2), Micro compute (covered by the $10/month compute credit), Spend Cap ON. Free is rejected for production: 50 MB per-file hard cap (phone videos exceed it), 7-day inactivity pausing, 1 GB storage / 5 GB egress, fixed 2 GB disk. Expected baseline: USD $25/month (+$4 only if the IPv4 add-on is needed).

2. Database connections (keep the repo's split of DATABASE_URL vs QUEUE_DATABASE_URL):
   - apps/worker (long-lived Node process running FFmpeg + pg-boss): use the DIRECT connection `postgresql://postgres:<pw>@db.<ref>.supabase.co:5432/postgres?sslmode=require` when the worker host has IPv6 egress; otherwise use shared-pooler SESSION mode `postgresql://postgres.<ref>:<pw>@aws-<n>-ap-southeast-2.pooler.supabase.com:5432/postgres` (copy the exact host from the Connect dialog). Do not buy the IPv4 add-on unless both direct and session mode are unworkable.    - Connection budget on Micro: Postgres max 60 (shared with Auth/Storage/PostgREST), pooler default pool size 15 per role. The current worker settings (pg.Pool max 8 + pg-boss max 6 = 14) nearly exhaust the 15-connection session pool; reduce to pg.Pool max 4 and pg-boss max 3 for the worker (and raise the Dashboard Pool Size to ~30 if needed, staying under 80% of 60).
   - apps/web (Next.js): if deployed serverless (Vercel/Sydney), use shared-pooler TRANSACTION mode on port 6543 with pool size 1, `sslmode=require`, and never use named prepared statements (do not call drizzle `.prepare()`; node-postgres unnamed `$1` queries are fine). The web app's pg-boss producer (`supervise: false`, unnamed queries, xact-scoped advisory locks) works through transaction mode. If the web app runs on the same VPS as the worker, just use the same direct/session string. The dedicated PgBouncer pooler (Pro+) is unnecessary at this scale.
   - Use `sslmode=verify-full` with the downloaded project root cert where the driver supports it; enable "Enforce SSL" in Database settings.

3. Media storage: use Cloudflare R2 for all blobs (source footage, analysis frames, previews, exports) via the existing S3Store: STORAGE_DRIVER=s3, S3_ENDPOINT=https://<account_id>.r2.cloudflarestorage.com, S3_REGION=auto, S3_FORCE_PATH_STYLE=true, one private bucket created with location hint `oc` (Oceania), API token scoped Object Read & Write to that bucket. Rationale: the worker re-downloads multi-GB source footage from object storage for every render and the owner downloads large exports; on Supabase that is billable uncached egress ($0.09/GB after 250 GB, and private-bucket signed URLs rarely hit the CDN), whereas R2 egress is free and storage is $0.015 vs $0.0213 per GB-month with a 10 GB free tier. Presigned GET URLs stay short-lived (15-60 min; both providers cap at 7 days). Multipart via lib-storage (8 MB parts) is supported on both.
   - Alternative (single-vendor): Supabase Storage via S3 protocol with the same driver: enable the S3 connection in Storage Settings, generate S3 access keys (server-only; they bypass RLS), S3_ENDPOINT=https://<ref>.storage.supabase.co/storage/v1/s3, S3_REGION=ap-southeast-2 (as shown on the S3 settings page), S3_FORCE_PATH_STYLE=true, raise the Global file size limit (Pro) to e.g. 20 GB and set a bucket-level limit/MIME allowlist, keep the bucket private. Acceptable for a small catalogue but budget for egress; do not rely on supabase-js createSignedUrl since the app serves presigned S3 GETs itself (7-day server cap).
   - Keep LocalDiskStore for dev; the S3Store already abstracts both targets so switching is config-only.

4. ## Commercially licensed music options (royalty-free libraries, CC sources, platform-native sound libraries, music/AI-music APIs) for Studio Assistant's social-video renderer, incl. TikTok Commercial Music Library and Meta Sound Collection rules for business accounts
Confidence: **medium**

**Decision:** Decision for Studio Assistant: build a provider-agnostic 'Licensed Catalogue' whose source of truth is owner-uploaded tracks plus a per-track licence record ('licence passport'), and treat any provider API as an optional adapter that writes into the same model. Do NOT build the product around a library API: Epidemic Sound (partnership agreement + Order Form; free plan is prototyping-only, 50 downloads, no commercial licence) and Artlist (Enterprise-only Music API) are unrealistic for a one-shop app; Uppbeat's API is unreleased; Musicbed, Pixabay (audio), YouTube Audio Library and FMA have no API; Freesound's API needs a negotiated licence for commercial use; ccMixter's Query API is CC-only. 

Phase 1 (ship now): (1) Owner buys ONE business-eligible subscription in the shop's legal/trading name and downloads tracks manually; Studio Assistant stores the files and the licence passport. Shortlist by cost/coverage for an Ivanhoe barber posting organic Reels/TikToks with occasional boosts: Soundstripe Business (US$999/yr; paid social 'local audience') or Pro (US$239/yr; 'commercial content created by individuals, including client projects and digital ads' - confirm with Soundstripe that a sole-trader shop's own brand content qualifies), Epidemic Sound Commercial (publish 'anywhere online', digital ads, one user, business turnover cap), Uppbeat Business (US$34.99/mo yearly) or Pro (US$14.99/mo yearly), Artlist Pro/Max Business (never the Social plan), Musicbed Business (~US$99.99/mo). Free/CC sources allowed only as CC BY or CC0 (Pixabay, Incompetech CC BY, ccMixter lic=by/CC0, Freesound CC0/CC BY downloaded manually), never CC BY-NC, YouTube Audio Library standard-licence tracks, TikTok CML or Meta Sound Collection audio in exported MP4s. (2) Licence passport schema on music_tracks: provider (enum incl. owner_upload), provider_track_id/url, title, artist, duration/bpm/mood, licence_type (subscription | single_track | cc_by | cc_by_sa | cc0 | platform_only | standard_paid), licence_holder (business name), licence_account_email, plan_name, licence_ref_or_code (e.g. Uppbeat credit code, Epidemic track licence, Tribe of Noise certificate), purchased_at, licence_document_asset (PDF/receipt/screenshot upload), download_record_asset (Pixabay-style proof), permitted_platforms[] (instagram, facebook, tiktok, youtube, website, email, in_store), permitted_use_types[] (organic_social, paid_social, client_work), territory, term_type (perpetual_for_published_projects | requires_active_subscription | one_project), valid_until (nullable), attribution_required (bool), attribution_text (exact string to paste), claim_clearance_notes (safelisted channels / claim-release instructions / Content ID shield flag), prohibited_uses (free text), verified_by, verified_at. (5) Platform-native audio path: offer a 'music-free export' (dialogue/ambient only, normalised) so the owner can add TikTok Commercial Sounds or Meta Sound Collection audio inside the apps where those licences are valid; record that choice in the ledger as platform_native_audio. If Studio Assistant publishes to TikTok via the Content Posting API, render the mandated line 'By posting, you agree to TikTok's Music Usage Confirmation' before the publish button and keep the owner's confirmation in the ledger. For Instagram API publishing, poll the container's copyright status before publishing and surface BLOCK/MUTE results.

## Email sending for an Australian small business (Studio Assistant, barber in Ivanhoe VIC): Spam Act 2003/ACMA requirements, Resend vs Postmark capabilities and pricing, Gmail/Yahoo/Outlook sender requirements, and the consent/unsubscribe data model to implement
Confidence: **medium**

**Decision:** PROVIDER: Use Postmark (Basic plan, USD $15/month, 10,000 emails) as the primary provider, behind an `EmailProvider` adapter interface with Resend as the documented fallback. Reasons: (1) at a barber's volume (likely < 3,000/month) Resend Free is $0 but its 100 emails/day cap would spread a single campaign to a few hundred clients over several days, and Resend Pro ($20) costs more than Postmark Basic ($15); (2) Postmark gives provider-enforced compliance primitives the app can audit: separate Transactional and Broadcast message streams, automatic RFC 8058 one-click headers and unsubscribe link on the Broadcast stream (no need to build and risk-break our own one-click endpoint, which is exactly what ACMA fined Lululemon for), per-stream suppression lists with a Suppressions API and a SubscriptionChange webhook, batch sends of 500, 45-day message retention, npm `postmark` (ServerClient). (3) Neither provider offers an Australian region or AU data residency (Resend: 4 sending regions, nearest Tokyo, account data in the US; Postmark: US only). Accept US hosting, disclose it in the privacy notice. Use the Resend adapter only if Postmark approval is refused (then Resend Free for transactional + Pro $20 when campaigns need > 100/day; on Resend we must add both List-Unsubscribe headers ourselves on API sends and host the one-click POST endpoint, or use Resend Broadcasts/Segments which store contacts at Resend).

MESSAGE CLASSES (hard-coded in the app, one enum, enforced by a template linter):
- `transactional_factual` (booking confirmation, reminder, reschedule/cancellation notice, receipt): Postmark Transactional stream; content limited to facts + business name/contact details (Spam Act s 17 still applies); NO offers, discount codes, 'book your next visit' CTAs, social/promo links (Ticketek/DoorDash/Lululemon precedent). No consent needed and no Spam Act unsubscribe required, but keep a product-level 'reminders off' preference. Linter blocks promotional phrases and any link outside the booking-management page.
- `review_request` and `campaign`: treated as commercial electronic messages (conservative; ACMA treats surveys/free-offer messages as commercial): Postmark Broadcast stream only; require current consent; footer must contain business trading name, Ivanhoe VIC street address, phone, email, and the `{{{ pm:unsubscribe }}}` link; Postmark adds List-Unsubscribe/List-Unsubscribe-Post automatically. Max one review request per completed appointment, never to a suppressed/unsubscribed address.

DATA MODEL (Postgres):
1. `clients.email` (citext, normalised) + `clients.email_marketing_state` cached enum ('no_consent','express','inferred','withdrawn','suppressed').
2. `email_consents` (append-only ledger): id, client_id, email_snapshot, scope ('marketing' = campaigns + review requests; single scope so one unsubscribe withdraws all commercial email, per the TAB finding), status ('express'|'inferred'|'withdrawn'), method ('booking_form_checkbox'|'in_store_signup'|'website_form'|'verbal_recorded_by_staff'|'import_with_evidence'), consent_text (exact wording shown, unticked-by-default checkbox), evidence jsonb (form id/version, IP, user agent, timestamp, staff user id, attachment ref), granted_at, recorded_by, withdrawn_at, withdrawn_via ('one_click_post'|'link'|'reply'|'in_person'|'staff'|'provider_webhook'|'spam_complaint'). Rules: default and recommended state is `express`; `inferred` is allowed only for a client with >= 2 completed appointments in the last 12 months (app policy, not a statutory number) and auto-lapses to 'no_consent' when no completed appointment in 12 months; never email a client to request consent; 'verbal' consent is flagged as weak evidence in the UI.
3. `email_suppressions` (global, keyed by normalised email + scope): scope ('marketing'|'all'), reason ('unsubscribe'|'spam_complaint'|'hard_bounce'|'manual'|'invalid_address'), origin ('recipient'|'staff'|'provider'), provider_stream, provider_record_id, source_message_id, occurred_at, synced_to_provider_at. Hard bounce and spam complaint => scope 'all' (stop everything to that address); unsubscribe => scope 'marketing' (factual reminders continue, matching Postmark's per-stream model). Mirror both ways with Postmark: ingest SubscriptionChange (SuppressSending true/false) and Bounce/SpamComplaint webhooks; push staff-entered unsubscribes to the Broadcast stream via the Suppressions API (ManualSuppression, origin Customer) so Postmark also blocks them.
4. `email_messages` (send log, retained >= 24 months as compliance evidence; Postmark keeps only 45 days): id, client_id, to_email, message_class, stream, provider ('postmark'|'resend'), provider_message_id, campaign_id, template_key/version, subject, consent_id (FK to the consent relied on at send time), status ('queued','sent','delivered','delayed','bounced','complained','suppressed','failed'), timestamps per status.
5. `email_events` (raw webhook payloads, idempotent on provider MessageID + RecordType + ReceivedAt; webhook URL protected with HTTP basic auth + secret header; reject unknown record types gracefully).
6. `campaigns`: subject/body/template, audience_rule, scheduled_at, sent_at, counts, auto-pause thresholds.

SEND GATE (single function `assertCanSend(client, messageClass)` returning reason codes, called in the job worker, never bypassable from the UI): transactional_factual => email present, no 'all'-scope suppression, template passed factual linter. review_request/campaign => current consent in (express, inferred-and-not-lapsed), no suppression (any scope), Broadcast stream, footer identity block present, `{{{ pm:unsubscribe }}}` present, frequency cap honoured. Campaign sends use /email/batch in chunks of 500 with Promise.allSettled; record per-message results; auto-pause a campaign if complaints > 0.1% or bounces > 5% of delivered.

UNSUBSCRIBE HANDLING: process immediately (statutory maximum 5 business days; Gmail/Yahoo 48 hours/2 days): SubscriptionChange webhook => insert suppression + append 'withdrawn' consent row + update cached state within seconds; staff 'Unsubscribe' button for in-person/phone/reply requests does the same and calls the Suppressions API; the Reply-To is a monitored mailbox and the SOP says any reply saying unsubscribe/stop is actioned the same day. The unsubscribe facility must stay functional >= 30 days after each send (verify Postmark links do not expire; if self-managing, use a non-expiring HMAC token page that needs no login and asks for nothing but confirmation).

DOMAIN/AUTH: send only from the business's own domain (never @gmail.com From addresses): add Postmark DKIM TXT, custom Return-Path CNAME (SPF/DMARC alignment), SPF include for Postmark, DMARC `p=none` with rua reporting at launch, move to `p=quarantine` once reports are clean; register the domain in Google Postmaster Tools; keep complaint rate < 0.1%. One-click headers are strictly required by Gmail/Yahoo only for ~5,000+/day senders, but Postmark adds them on Broadcast anyway and they are good practice.

## Vertical video safe zones and export specs for TikTok and Instagram Reels (1080x1920) for Studio Assistant
Confidence: **medium**

**Decision:** Studio Assistant renders at exactly 1080x1920 (9:16, square pixels) and uses ONE layout model that is the conservative union of Meta's official percentages (14% top / 35% bottom / 6% sides) and the most conservative widely-cited reading of TikTok's official in-feed template (240 top / 660 bottom / 120 sides / 300 px right in the lower frame). Pixel decisions (origin top-left):

UI EXCLUSION BANDS (never place text, logos, CTAs, subtitles here):
- Top band: y < 270 (IG 14% = 269; TikTok 240).
- Bottom band: y >= 1248 (IG 35% = 672 px from bottom; TikTok 660).
- Side bleed: x < 120 and x > 960 everywhere (TikTok 120; IG 65).
- Right action-button column: x > 780 for y >= 840 (TikTok 180-px icon column inside the 120-px margin from y~840; IG lower-right block ~21%/227 px wide in the bottom 40%).

TEXT-SAFE RECTANGLES exposed to the planner/renderer:
- R_strict (default for everything): x 120-780, y 270-1248 (660 x 978). Any text box the renderer emits must be fully inside R_strict unless it qualifies for R_head.
- R_head (titles/hooks/logos whose box bottom <= 840): x 120-960, y 270-840 (840 x 570). This is clear of both platforms' button columns.
- Subtitles/captions: centred at x = 540, max width 480 (x 300-780), bottom-anchored with box bottom <= 1248 (default baseline band y 1100-1248), minimum font size 56 px, 2-3 words per line, drop-shadow or pill background for legibility. Centring at 540 with 480 width keeps them centred on screen while still inside R_strict.
- Logo/watermark: top-right of R_head, right edge at x 960, top at y 270 (clear of both top bars and the right-hand icons). Never a third-party-style watermark (hurts IG recommendations).
- Subject framing (soft, not enforced): keep faces/the haircut within y 270-1440 and x 0-940; the UI overlays are translucent so partial overlap of the subject is tolerable, text is not.
- Previews: overlay a dimmed-band PNG of the exclusion bands (two toggles: 'TikTok' and 'Reels') on the five preview renders so the owner can see what the apps cover; the exported file never contains the overlay.

EXPORT PRESET (single universal file for both platforms; FFmpeg):
- Scale/crop every source to 1080x1920 (crop, never letterbox; setsar=1). Do not export 4K (IG max width 1920 would reject a 2160-wide file).
- Video: libx264, -profile:v high, -level 4.1 at <=30 fps or 4.2 at 60 fps, -pix_fmt yuv420p, progressive, constant frame rate (-fps_mode cfr). Default 30 fps (satisfies IG Help 'minimum 30 FPS', IG API 23-60, FB Reels 24-60, TikTok API 23-60); offer 60 fps only when every source clip is >=50 fps; 24/25/50 fps sources are conformed to 30 (or 60). Closed GOP of 2 s (-g 60/-keyint_min 60 at 30 fps, -g 120 at 60 fps, -sc_threshold 0, open_gop=0), -preset slow, -crf 18 with VBV cap -maxrate 20M -bufsize 40M (30 fps) or -maxrate 24M -bufsize 48M (60 fps); peak stays under IG's 25 Mbps max and far above TikTok's 516/2,500 kbps minimums. Colour: SDR only, tag -color_primaries bt709 -color_trc bt709 -colorspace bt709 -color_range tv; tone-map HDR sources (iPhone HLG/Dolby Vision 8.4, PQ) to BT.709 at ingest (zscale/tonemap or libplacebo). No HDR export because TikTok's HDR handling is undocumented.
- Audio: AAC-LC, 48 kHz, 2 channels, 128 kbps (the literal IG value and FB '128kbps+'), loudness-normalised (-14 LUFS integrated target), single audio track.
- Container: MP4, -movflags +faststart+negative_cts_offsets -use_editlist 0 (moov atom at the front, no edit lists, per IG spec), one video + one audio track, .mp4 extension (TikTok web upload does not list MOV).
- Duration: min 5 s; templates target 15-60 s; hard cap 180 s (3 min) so the file is eligible for IG recommendation to new audiences and fits every TikTok creator tier (3-minute floor, max_video_post_duration_sec); warn when > 90 s (IG boost limit). For 90-180 s exports lower -maxrate to 12M so the file stays under 300 MB.
- File size guard: reject/re-encode if > 300 MB (IG API max); this automatically satisfies TikTok ads (500 MB), TikTok API (4 GB) and TikTok Studio (10 GB).
- Post-export validation (ffprobe): 1080x1920, yuv420p, h264 High@4.1/4.2, CFR 30 or 60, GOP <= 2 s closed, AAC 48 kHz stereo, bt709 tags, moov before mdat, no elst, duration 5-180 s, size <= 300 MB. Fail the job with a plain-language message if any check fails.
- Store the safe-zone constants in one shared module (packages/video/safe-zones) with the source citations as comments and a 'reviewed on' date, since both platforms change UI without notice; recheck roughly every 6 months by downloading TikTok's in-feed safe-zone ZIP and Meta's Reels safe-zone checker and re-measuring.
